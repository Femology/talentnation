## Study notes

An algorithm is a procedure, decomposition splits a goal into smaller tasks, and sequencing orders them. An atomic step at a chosen abstraction level can hide smaller operations; database atomicity has the stronger all-or-nothing meaning.

```text
Appointment request
  -> validate date and details
  -> authenticate patient
  -> check available slots
  -> obtain confirmation
  -> reserve atomically
  -> verify saved booking
  -> communicate outcome
```

If validation fails, explain and stop or offer alternatives. Independent tasks can sometimes run concurrently; dependent tasks must respect their ordering. A hypothetical five-day minimum notice rule rejects tomorrow's booking before execution.

```python
def next_action(verified, available, confirmed):
    if not verified:
        return "Authenticate"
    if not available:
        return "Offer alternatives"
    if not confirmed:
        return "Ask for confirmation"
    return "Proceed to secure booking"
```

### FDE caveats
Availability can change between checking and committing. Enforce exclusive reservations with a database constraint or appropriate transaction/concurrency control. If a booking times out, preserve the request ID, mark UNKNOWN, and verify before safe retries. Choose identity checks proportional to actual needs; don't collect full KYC unnecessarily. Use password-hash verification, not plaintext passwords. Not every if needs an explicit else.
